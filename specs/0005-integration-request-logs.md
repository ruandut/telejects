# 0005 — Integration request logs

- **Status:** Done
- **Depends on:** 0003, 0004
- **Django apps:** new `integration_logs` (the log, its per-company limit, the Logs section's
  API); `integrations` and `feasibilities` write to it
- **Touches:** frontend / backend / jobs

## Why
When a provider answers strangely ("InProgress" media from Vodacom, a 503 from MTN), the only
way to see what was sent and what came back today is a database shell. Each provider check also
keeps the provider's whole raw answer for ever, which for a large Vodacom run is far more than
anyone needs. A company's admins should be able to open a Logs section in the portal, find the
request behind a strange result, and see exactly what went to the provider and what came back.
What is kept is capped per company, so it can't grow without bound.

## Scope
- In:
  - **Every provider request is logged:** feasibility checks, product syncs and connection
    tests, with the request (method, URL, headers, body) and the response (status, headers,
    body), duration, outcome and error, and links to the run, check or sync it belongs to.
  - **Secrets never reach a log:** a connection's secrets are redacted, and for a platform
    connection (0004) Telejects' settings are redacted too, as companies never see them.
  - **A per-company limit:** a company keeps its last **5,000** requests by default; older ones are
    removed as new ones arrive. Platform staff raise or lower it per company in Django admin.
    The default lives in the app's config (settings), not in code.
  - **A Logs section in the portal:** a list, newest first, with search and filters; a detail view
    showing the request and response formatted; live updates as requests are made.
  - **The limit is shown** on the Logs page, with why older entries disappear.
  - Provider checks stop keeping raw answers themselves; the log is where they live.
- Out (later specs):
  - Logging the portal's own API requests (this is provider traffic only).
  - Exporting or downloading logs.
  - Logs of platform-level work that belongs to no company (Telejects' account credential
    checks): those show their outcome on the platform account in Django admin, as now.
  - Alerts on error rates.

## Design notes

### The app
A new domain app, `apps/integration_logs`, so the log, its retention and its screen are one
concern of their own. It sits below `integrations` and `feasibilities`, which both call it to
record requests, so it imports only `core` and `realms` and refers to their rows by id (with a
snapshot of the connection's name). Its `AppConfig` reads `INTEGRATION_LOGS_DEFAULT_LIMIT` from settings
(default 5,000, from `.env`, generated by `init_env.sh`).

### Data
- **`IntegrationLog`** (`TenantModel`): connection (`SET_NULL`, plus its name at the time), the
  operation (`check_feasibility`, `sync_products`, `test_connection`), what it belongs to (feasibility
  run and check, or sync run), credentials (`own` / `platform`), connector key and definition
  version, method, URL, request headers and body, response status, headers and body, duration,
  outcome (`ok` or an error kind) and error message, attempt number, created at.
  Retries are separate entries (attempt 1, 2, 3).
- **`LogRetention`** (`TenantModel`, one per company, created on demand): `max_entries`. Absent
  means the default. Staff edit it in Django admin (with the company's current count shown);
  a company can't change it.
- **Bodies are capped** at 256 KB each; a larger one is cut and marked "truncated (N KB)".
- `ProviderCheck.calls` is removed (migration), and the check links to its log entries instead.
  `SyncRun` links to its entries too.

### Recording
- The engine reports every HTTP exchange (also failed ones: timeouts, connection errors,
  non-JSON bodies) to a recorder the caller passes in, after redaction. The Demo and any Python
  connector record their calls the same way.
- Redaction: the connection's secret values anywhere in URL, headers, bodies and error messages;
  for platform connections, also Telejects' setting values. Authorization-style headers are
  redacted by name as well (`Authorization`, `X-API-KEY`, `api-key`, the definition's auth
  placements).
- Entries are written in their own small transaction, so a failing check still logs what it
  sent. Writing a log never fails the provider call: a logging error is reported and skipped.

### Retention
- After writing, the company's entries beyond its limit are deleted, oldest first, in the same
  transaction (a cheap delete by id below the Nth newest).
- Lowering the limit in Django admin prunes at once; raising it keeps what's there.
- A run of 10,000 sites therefore leaves only its last 5,000 requests (with the default) in the
  log. Its results are unaffected: they're stored with the run.

### API (realm-scoped, under `/api/integration-logs/`)
- List, paged, newest first, with filters: connection, operation, outcome (ok / error / a
  specific error kind), HTTP status (or class: 2xx, 4xx, 5xx), feasibility run, date range, and a
  free-text search over the URL, request and response bodies and error message.
- Detail: the full entry.
- `GET .../limits/`: the company's limit, how many it keeps now, and the default.
- No create, edit or delete from the API: the log is written by the system and pruned by its
  limit.

### Live updates
A topic `integration_logs` (see `apps/realms/live.py`): new entries are pushed to subscribers
with the list's serializer, at most about once a second, as the run pages do (0003). Access
is checked like the API.

### Portal
- **Logs** in the sidebar, under Integrations, for whoever may see logs.
- The list: time, connection, operation, method and path, HTTP status, duration, outcome, with
  the filters above and a search box. A banner: "Telejects keeps the last 5,000 provider requests
  for Northwind Fibre. Older ones are removed as new ones arrive." (with the company's number).
- A detail view: request and response side by side (stacked on a phone), JSON formatted and
  collapsible, headers, timing, and links to the run (and site) or connection it belongs to.
- A provider error on a run's site and a failed sync link to their log entries, while those are
  still kept.

### Who may do what
A new permission code, `integrations.logs`: "See the requests made to providers and their
answers". Admin has it; Project manager gets it (drafted, see Decisions); Viewer doesn't.

## Scenarios

### AT-0005-01 — Every provider request is logged
- When a run checks sites, a connection is tested, or its products are synced
- Then each request to the provider appears in Logs with what was sent, what came back, how
  long it took, and whether it worked

### AT-0005-02 — Failed requests are logged too
- When a provider times out, refuses the credentials, answers 503 or answers something that
  isn't JSON
- Then the request is logged with the error, and every retry is its own entry

### AT-0005-03 — Logs never show a secret
- Given connections with their own keys, and one using Telejects' account
- Then no secret appears in any entry, list, search result or detail, and for the Telejects
  account its settings don't either
- And searching for a secret's value finds nothing

### AT-0005-04 — I find the request I'm looking for
- When I filter by connection, operation, outcome, HTTP status, run or date, or search for text
  in the request or response
- Then only matching entries are listed, newest first

### AT-0005-05 — I see the whole exchange
- When I open an entry
- Then I see the request and the response, formatted, with headers, timing and links to the
  run, site or connection it belongs to

### AT-0005-06 — A company keeps its last 5,000 requests
- Given a company at its limit
- When more requests are made
- Then the oldest entries are removed, so it keeps exactly its limit, and another company's
  entries are untouched

### AT-0005-07 — I can see the limit and why entries go
- When I open Logs
- Then I see how many requests my company keeps, and that older ones are removed as new ones
  arrive

### AT-0005-08 — Staff change a company's limit
- When platform staff set a company's limit to 20,000 in Django admin
- Then that company keeps up to 20,000, Logs shows 20,000, and other companies keep 5,000
- And lowering it removes the oldest at once

### AT-0005-09 — New requests appear as they happen
- Given I have Logs open
- When a run makes requests
- Then they appear at the top without reloading

### AT-0005-10 — From a strange result to its request
- Given a run's site shows a provider error
- When I follow "See the request"
- Then the log entry of that call opens (or I'm told it's no longer kept)

### AT-0005-11 — Only people with the permission see logs
- Given I'm a Viewer
- Then I don't see Logs, and its API refuses me

### AT-0005-12 — Another company's logs stay out of sight
- Given another company has log entries
- Then none appear in my list, search or counts, and their detail is a 404

## Decisions
Decided with Ruan:
1. Logs are a section of the portal, searchable and filterable.
2. A company keeps its last 5,000 requests by default (raised from 200 by Ruan after the
   build); staff change it per company in Django.
3. The limit is shown in the portal, with why older entries disappear.
4. A spec of its own, logging every integration request and response.

5. A new app, `integration_logs`.
6. A new permission, `integrations.logs`, for Admin and Project manager.
7. Bodies capped at 256 KB each.
8. Raw answers move out of `ProviderCheck` into the log, capped with it.
9. The default limit comes from `.env` (`INTEGRATION_LOGS_DEFAULT_LIMIT`, 5,000).

## Implementation notes

Built as approved.

- **App (`backend/apps/integration_logs/`):**
  - `models.py`: `IntegrationLog` and `LogRetention`.
  - `services.py`: `Recorder` (redacts once more, caps bodies, writes each entry in its own
    transaction, prunes, publishes; a logging error is logged and skipped), plus `prune`,
    `limit_for` and `set_limit`.
  - `views.py`: the read-only API with filters, search and `limits/`.
  - `live.py`: the `integration_logs` topic.
  - `admin.py`: limits per company with the current count, and read-only entries.
  - `apps.py`: `default_limit` from `INTEGRATION_LOGS_DEFAULT_LIMIT`, which `init_env.sh` writes as
    5000 and appends to an existing `.env`.
- **Engine:**
  - `CallRecord` gains response headers, duration and error.
  - `build_connector(..., recorder=)` reports every exchange: successes, HTTP errors, timeouts,
    connection failures and non-JSON answers. The Demo connector reports its calls too.
- **Callers:**
  - `integrations.services.recorder_for` and `connector_for(connection, recorder)`. A platform
    connection's recorder also hides Telejects' setting values.
  - Header names that carry credentials are redacted.
  - Each feasibility attempt, sync and test is its own entry (`attempt` counts retries).
  - `ProviderCheck.calls` is removed (`feasibilities/0006`).
- **Links:**
  - A run site's errors and a sync carry `log`, the id of their latest kept entry.
  - The run page has a "Requests" button that opens the log filtered to that run.
- **Portal:**
  - `features/logs/` and `routes/_app/logs/`: the list, with the limit banner, search, filters
    by connection, operation, outcome, status, date and run, live entries and paging.
  - The detail view shows the request and response formatted, with headers, timing and links.
  - "Logs" appears in the sidebar for `integrations.logs`.
- **Tests:**
  - `apps/integration_logs/test_logs.py`: scenarios 01–11, plus the body cap, read-only API and
    "a logging failure never breaks the call".
  - `apps/realms/test_isolation.py`: scenario 12 and the logs routes in the shared guards.
  - The fake providers gained timeout and non-JSON switches.
- **Checked in the running app** (a throwaway company, deleted afterwards):
  - live Vodacom calls on Telejects' account, logged with the key and its calling-system
    setting redacted;
  - failing Demo calls appearing live with each attempt;
  - the detail view, and the links from a run's error and to a run's requests;
  - phone width and both themes.
  - The provider calls ran from a shell with the new code, because the running worker predated
    the change. Its `feasibility-check` would fail against the migrated database until it's
    restarted.
